## Memory decision

| Scope | Threshold | Purpose |
| --- | ---: | --- |
| PR #148 sampled worker tree | 153.60 GiB (80%) | Historical gate |
| Proposed E1 sampled worker tree | 163.20 GiB (85%) | Operational acceptance |
| Proposed E1 full Slurm job cgroup | 172.80 GiB (90%) | Guard and operational acceptance |
| Required effective job cgroup ceiling | 192 GiB | Slurm allocation verified on the compute node |

The highest historical h400 worker-tree peak would clear the proposed
worker threshold by about 2.96 GiB. A 16% reserve would clear it by about
1.04 GiB. Worker-tree RSS and full-job cgroup memory measure different
scopes and can diverge. A Slurm MaxRSS value has its own accounting scope.
Report all three separately.

Before a private pilot, qualify the job-local cgroup v2 path against the
Slurm job identity and ancestors. Check that the effective limit is exactly
192 GiB, that `memory.current`, `memory.peak` and `memory.events` are
readable, and that the collector can retain evidence after a guarded
termination. The planned guard monitors current job memory, stops the owned
solver step at the threshold and retains the receipts, with no retry. The
terminal gate also checks the job peak and zero OOM-event deltas. A rapid
allocation can still outpace polling. If job-scoped accounting cannot be
qualified, keep the 15% profile unqualified until an equivalent can be
verified on NPAD.

At 192 GiB, keep one solver process, bind the worker, cap unrelated
numerical-library thread pools, and stream exports without holding extra
copies of the decisions. Qualify the observer and export path before using
them with private inputs. If a pilot exceeds either gate, retain the attempt
and pause progression. Options for a separate decision are a qualified
lower-memory model-transfer path or a higher-memory common allocation.
Either requires preserving original receipts and verifying comparability.
A memory stop leaves that thread level unresolved. Time-limit outcomes are
valid operational observations when all receipts close, with solution quality
reported separately.

## Receipt review and launch boundary

`python -B -I scripts/pyomo_h400_e1.py plan` prints the proposed settings.
`review BUNDLE --campaign-sha SHA256 --source-sha COMMIT` checks the four
collections, their archives, the effective settings and the two memory
criteria. Each collection contains `campaign_observation.json` and
`memory_receipt.json` inside its archive. The latter also sits beside the
archive for inspection. The public cgroup probe establishes measurement
availability. Live qualification of the collector and guard precedes the
private launch recipe. A passing receipt review only classifies the four E1
observations.
