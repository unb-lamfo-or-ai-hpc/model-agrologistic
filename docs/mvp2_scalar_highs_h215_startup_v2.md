## How initialization changes

The Slurm numeric step starts a small Python script with -B -I -S. Before site
initialization or application imports, it checks the small source/plan/job
receipts, the pinned bootstrap/driver bytes, output/source layout, job/step IDs
and process start ticks. It publishes entry.json and starts the original
input_build clock. These receipts do not assert that full verification is done.

The existing supervisor queries the exact Slurm step and checks owner, node,
allocation and CPU binding before publishing the matching release. Its original
45-second unbound-entry deadline and targeted cleanup remain unchanged.
Only after that release does the worker initialize the existing site packages,
import the application, verify all tracked source bytes and interpreter/package
fingerprints, recheck all input hashes, verify tools, identify HiGHS and run
the public mathematical/medium gate. Private population construction follows
only after those checks pass. No solver, dependency or environment is changed.

Every startup stage has an exclusive begin record and a complete or failed
record, with source/plan/job/process identity and elapsed/duration seconds:

1. Bootstrap identity and exact release.
2. Site initialization and application import.
3. Plan validation and complete source-byte verification.
4. Interpreter/package fingerprints and original input hashes.
5. Tool verification, native identity, public qualification and runtime receipt.

A killed process leaves its last begin record. A Python exception retains its
failed-stage kind and stderr traceback. Portable collection reports absent,
incomplete, failed, rejected or complete startup separately from numerical
quality. Missing products are reported as not_returned rather than a fabricated
solver error. Successful startup alone never certifies a solution.

All initialization, release wait, public controls, input reads, Pyomo construction
and native transfer count within the original 3600-second input/build ceiling.
The initial phase receipt is reused, not restarted when model construction begins.
The whole numeric worker and original supervisor continue to bound elapsed time;
a late or hung stage remains a partial observation and cannot trigger a retry.
