## Frozen prospective comparison

`experiments/mvp2_scalar_r3a_h215.yaml` explicitly specifies scalar DET then STO
on the same separately selected/checksummed h215 workbook. Do not execute the
historical version1 campaigns or silently convert their hierarchy fields.

Both modes use the same resolved loader, model, solver, limits and input bytes;
only experiment name and `model.mode` differ. DET retains original deterministic
arrays, not expected stochastic demand. STO proposes the existing three-by-three
supply/demand Cartesian design; actual probabilities are read from the selected
input under the unchanged loader. Real preflight must verify215 warehouses,
60 periods and1/9 effective scenarios, the size guard, selected routes and finite
mathematical contract. The hashes do not certify input suitability without ETL.

The proposal preserves OSRM-primary distances, connectivity-preserving Pareto20%,
no direct origin/customer arcs, warehouse transshipment, daily capacity coupling,
three separate slacks, thesis-dynamic penalties and the original validation
tolerances. No fourth slack, EVPI/VSS, priority stage, scenario averaging or
automatic private-input generation is introduced. Expected operating cost and
artificial penalties remain separately labelled; positive slack is not installed
capacity or proof of no-slack infeasibility. DET/STO costs are not VSS/EVPI.

The proposed solver profile is Gurobi, one scalar native call/arm, global3600s,
MIPGap0.01, seed42, four threads, compaction off, no IIS run or extra optimizer
call, SoftMemLimit160 **decimal GB**, bounded resource diagnostics every5s.
Four threads is a conservative starting proposal, NOT a scalar optimum/ranking.
All these prospective selections require researcher confirmation with the input
and resource envelope. No parameter or budget was silently inherited as approval.
